# RFC 0016 — Rust and Zig language bindings for libdb

- Status: Draft (design + plan; implementation gated on acceptance)
- Target: the development line (post the first LTS, `v2026.10.7`)
- Scope: two new `lang/` bindings — `lang/rust/`, `lang/zig/` — that expose the
  libdb C API idiomatically, with tests, getting-started guides, reference
  docs and API docs in each language's native format.

This RFC designs both bindings against the **verified** C API surface
(`test/bench/.../capi_survey` methodology; sizes and flag values re-measured on
a FreeBSD HEAD build at `5e00a8b5e`, DB_CALVER 2026.10.7: DB=1744, DBC=552,
DB_ENV=2088, DB_TXN=336, DBT=40; soname `libdb-2026.0.so`). It lays out the
tradeoffs and the options so the shape can be chosen before code is written.

---

## 1. Goals and non-goals

**Goals.** For each of Rust and Zig, provide a binding that is: *complete* over
the access-method / environment / transaction / cursor / sequence surface a real
application uses; *efficient* (zero-copy where the C API allows, no needless
allocation on the hot path); *safe* in the language's own terms (Rust: the type
system enforces the lifecycle rules in §7 of the survey; Zig: explicit, checked
in safe builds, documented where it cannot be); and *intuitive* — the mapping
from a C concept to its binding form is obvious and uniform, so a reader who
knows one knows all of them.

**Non-goals (v1).** Replication / repmgr (DB_CHANNEL, DB_SITE, rep_* — large,
niche, and callback-heavy); the DB_MPOOLFILE raw buffer-pool API (an engine-
internal surface, not an application one); `DB_DBT_USERCOPY` (no public setter
exists — survey §5); the SQL and DBM compatibility layers. These are additive
later and must not force a redesign — the layering in §4 keeps them so.

**North-star constraint.** The binding must not change the C library. It is a
pure consumer of `db.h` + `libdb-2026.0.so`. The structs are opaque (survey §8),
so the binding depends on **method-pointer signatures and the constants**, not
struct layout; the recorded sizes can move under a stable soname and the binding
is unaffected. The only struct a binding mirrors is `DBT` (`#[repr(C)]` /
`extern struct`), because the app fills it in.

---

## 2. The three-layer shape (shared by both languages)

Both bindings use the same three layers. This is the single most important
design decision: it keeps the unsafe FFI in one small place, lets the safe layer
be purely additive, and makes the two languages structurally parallel so the
docs and tests mirror each other.

```
  Layer 0  raw C          db.h  +  libdb-2026.0.so            (the library)
  Layer 1  -sys / c.zig   1:1 extern decls, opaque pointers,  (unsafe, generated
                          constants, the DBT struct            or hand-checked)
  Layer 2  idiomatic API  handles as owning types, Result/    (safe, hand-written,
                          error-union, lifetimes, iterators    the thing users touch)
```

- **Layer 1 is mechanical and verifiable.** It is the method-pointer signatures
  and the constants, nothing else. For Rust this is a `libdb-sys` crate; for Zig
  it is a `c.zig` (or a thin `@cImport`). Either can be *generated* (bindgen /
  `zig translate-c`) or *hand-written against the survey*. See §3 for that
  tradeoff — it is the biggest open choice.
- **Layer 2 is where all the judgement is.** Everything in §5–§8 lives here. It
  calls Layer 1 and exposes nothing unsafe for the common path.

A caller uses only Layer 2. Layer 1 is published (so an advanced user can reach
the raw API for something v1 didn't wrap — e.g. replication) but is marked
clearly as unsafe/raw.

## 3. The central tradeoff: generate Layer 1, or hand-write it?

| | Generate (bindgen / `zig translate-c`) | Hand-write against the survey |
|---|---|---|
| Correctness vs the installed header | Exact by construction; re-reads the real `db.h` | Must track header changes by hand; a drift gate is required |
| Build dependency | Needs libclang (bindgen) at build time, or a vendored pre-generated file | None beyond `cc`/`zig` |
| Opaque handles | bindgen emits the full struct bodies unless told they're opaque; must pass `--opaque-type` for each handle or it bakes in the (changeable) layout | We *choose* opaque pointers; immune to layout |
| Method pointers | bindgen reproduces the func-pointer fields faithfully | We transcribe only the ~120 we wrap |
| Reproducible / offline builds (what a DB engine's users want) | Fragile (libclang version skews the output) unless the generated file is vendored and checked in | Trivially reproducible |
| Surface completeness | Everything, including the 788 setters and all repl | Only what we wrap (fine — Layer 2 is curated anyway) |

**Recommendation (both languages): vendor a *generated-then-frozen* Layer 1,
regenerated by a committed script, guarded by a drift test.** Concretely:

- Generate once (bindgen for Rust, `zig translate-c` for Zig) *with the handle
  structs forced opaque*, from the installed `db.h`. Commit the output.
- Commit the generator invocation (`lang/rust/sys/regen.sh`,
  `lang/zig/regen.sh`) so it is reproducible, not folklore.
- A CI test (`lang/*/test` + a `run_*` gate) compiles a tiny C program that
  prints `sizeof` of each wrapped struct **is irrelevant** (opaque) but asserts
  every *constant* the binding bakes in still equals the header's value, and that
  every method pointer the binding calls still has the expected arity. This is
  the teeth: the C library can change a flag value or add a method and the gate
  catches a stale Layer 1 — exactly the drift problem the hand-written option has,
  but automated. (Mechanism: generate a C file from the binding's own constant
  list, `#error` if any disagrees with `db.h`.)

This gets generation's correctness and hand-writing's reproducibility, and the
drift gate means neither language silently rots against the header. **Option B**
if the team prefers zero build-time codegen even once: hand-write Layer 1 from
the survey and rely entirely on the drift gate — same safety, more initial
transcription, no bindgen/translate-c dependency ever. The RFC is written so
either choice is invisible to Layer 2.

## 4. Mapping the C object model to each language

The C API is an object system: an opaque handle + a table of method pointers,
every method taking its handle first, returning `int` (survey §1). Both bindings
wrap each handle in an owning type whose methods call through the pointers and
whose destructor calls the handle's `close`/`commit`/`abort` exactly once.

| C handle | Rust type | Zig type | Created by | Destroyed by |
|---|---|---|---|---|
| `DB_ENV *` | `Env` | `Env` | `Env::create` → builder → `open` | `Drop` / `deinit` → `close` |
| `DB *` | `Db` | `Db` | `env.database()` builder → `open` | `Drop` / `deinit` → `close` |
| `DBC *` | `Cursor<'txn>` | `Cursor` | `db.cursor(...)` | `Drop` / `deinit` → `close` |
| `DB_TXN *` | `Txn` | `Txn` | `env.begin(...)` | `commit`/`abort` (consume self) |
| `DB_SEQUENCE *` | `Sequence` | `Sequence` | `db.sequence(key)` | `Drop` / `deinit` → `close` |
| `DBT` | `&[u8]` in / `Val` out | `[]const u8` in / `Val` out | n/a (mirrored struct) | n/a |

### Rust

- Handles are newtypes owning the raw pointer; `Drop` calls close once (idempotence
  guarded by taking the pointer). `close` can also be called explicitly and
  **consumes `self`** (survey §7: handle dead after close).
- **Lifetimes encode the ownership DAG** (survey §7: `DB_ENV ⊃ DB ⊃ {Cursor,
  txn-ops}`): `Db<'env>` borrows the `Env`, `Cursor<'txn, 'db>` borrows both the
  txn and the db, so the compiler refuses a cursor outliving its transaction —
  the exact rule the C docs state in prose, enforced for free.
- **Send/Sync by the DB_THREAD rule** (survey §7): `Env`/`Db` are `Send + Sync`
  **only when opened with `DB_THREAD`** — expressed by making the free-threaded
  constructor return a `Db` that is `Sync` and the plain one a `!Sync` `DbLocal`,
  or (simpler v1) always require `DB_THREAD` for the safe multi-threaded API and
  document the single-threaded escape hatch. `Txn`, `Cursor`, `Sequence`,
  `LogCursor` are `!Sync` always (C says "not free-threaded").
- Errors: `Result<T, Error>` where `Error` is an enum over the DB_* codes +
  `Errno(i32)` + a captured message string (from `set_errcall`). The expected
  negatives are demoted (§6).

### Zig

- Handles are structs holding the raw pointer; `deinit()` calls close. Zig has no
  destructors, so the lifecycle is **explicit** — `defer env.deinit()` is the
  idiom, shown in every doc example. Safe builds (`Debug`/`ReleaseSafe`) get a
  `debug.assert` that a handle is not used after close (a poisoned sentinel in the
  struct); release-fast omits it.
- The ownership DAG is **documented and assertion-checked**, not type-enforced
  (Zig has no borrow checker). `Cursor` holds a pointer to its `Txn`; in safe
  builds `txn.commit()` asserts no open cursors remain (a count on the txn).
- Threading: documented. The `Env`/`Db` carry a comptime or runtime flag for
  whether `DB_THREAD` was set; the cross-thread share helpers assert it.
- Errors: Zig **error unions**. `error{NotFound, KeyExist, Deadlock, ...}` for the
  DB_* set, plus a side-channel for errno and the captured message (Zig errors
  carry no payload, so the numeric errno/message is read from the `Env` after an
  `error.System`, mirroring how `std` surfaces `errno`). Expected negatives
  demoted (§6).

## 5. DBT — the ergonomic crux (survey §2)

The DBT memory regimes drive the whole value-facing API. Both bindings expose
**three input forms and three output forms**, chosen to make the common case
zero-copy and safe and the advanced cases reachable.

**Input (put / key / data in):** the app points DBT at borrowed bytes for the
duration of the call. Rust: `impl AsRef<[u8]>` / `&[u8]`. Zig: `[]const u8`. No
copy, no allocation. The binding guards `size==0`/`data==NULL` (survey §2: this
exact shape was real UB in the library).

**Output (get / cursor get):** the hard part. Default get returns a pointer into
DB-owned memory valid only until the next op (survey §2). Three forms:

1. **Copy-out (default, safest).** The binding uses `DB_DBT_MALLOC`, hands back an
   owned `Vec<u8>` (Rust) / caller-allocator `[]u8` (Zig), frees the DB buffer.
   Simple, always correct, one allocation per get.
2. **Into-caller-buffer (`DB_DBT_USERMEM`, zero-alloc).** Caller passes a mutable
   slice; on `DB_BUFFER_SMALL` the binding reports the needed size so the caller
   grows and retries. Rust: `get_into(&mut [u8]) -> Result<Need<usize>, _>`. Zig:
   `getInto([]u8) -> error{BufferSmall}!usize`. This is the hot-path form.
3. **Borrowed (`&[u8]` tied to a short lifetime).** For the default DB-owned
   pointer: Rust can expose `with_value(|&[u8]| ...)` — a closure that borrows the
   bytes for exactly the window they are valid (the lifetime cannot escape). Zig
   documents the validity window and returns a slice the caller must consume
   before the next op. This is zero-copy *and* zero-alloc but demands care; it is
   the advanced form.

**Bulk (`DB_MULTIPLE_*`, survey §2):** reimplemented as a **native iterator** over
the returned buffer (pure pointer arithmetic, sentinel `(u32)-1`), so a bulk get
yields `(key, value)` pairs with no per-record allocation. Rust: `impl Iterator`.
Zig: a `next()` iterator struct. This is where the binding beats a naive
one-call-per-record loop and should be front-and-center in the "efficient" story.

**Partial (`DB_DBT_PARTIAL` + dlen/doff):** a `Partial{offset,len}` option on get
and put. Rare; expose but don't clutter the common signatures.

## 6. Error model (survey §3)

One decoder, shared shape:

- `0` → `Ok(())` / no error.
- `< 0` and in `-30,999..-30,800` → a typed DB error variant.
- `> 0` → OS errno.

**Demote the control-flow negatives so they are not "errors":**

| C code | Rust | Zig |
|---|---|---|
| `DB_NOTFOUND` | `get` → `Ok(None)`; cursor → iterator ends | `error.NotFound` only where a value was required; `null` for optional/EOF |
| `DB_KEYEXIST` | `put(NOOVERWRITE)` → `Ok(Put::Exists)` | returns a `PutResult` enum |
| `DB_BUFFER_SMALL` | `get_into` → `Err(Need(n))` or an `Ok(TooSmall(n))` | `error.BufferSmall` + size via out-param |
| `DB_LOCK_DEADLOCK` | `Err(Error::Deadlock)` — documented retry | `error.Deadlock` |

The retry-on-deadlock loop is so central to transactional BDB that both bindings
ship a helper: Rust `env.transact(|txn| { ... })` that runs the closure, commits,
and on `Deadlock` aborts + retries (bounded); Zig `env.transact(ctx, fn)` same.
This is the single most important ergonomic win over raw C and belongs in the
getting-started guide's second example.

Diagnostics: wire `set_errcall`/`set_msgcall` through the §7 trampoline to capture
DB's human-readable strings and attach the last one to the returned error
(Rust: `Error::message()`; Zig: `env.lastError()`), so a failed call explains
itself the way the C `err`/`errx` would have printed.

## 7. Callbacks — the trampoline (survey §5, §cxx/§java)

Every app-supplied callback (comparators, hash, secondary-index extractor,
feedback, event-notify, errcall) uses one mechanism, identical in both languages
and lifted straight from the C++/Java bindings:

1. Stash the host closure/function behind the handle's reserved slot:
   `db->api_internal` (DB, DB_TXN, DB_SEQUENCE) and `dbenv->api1_internal`
   (DB_ENV) — the binding claims `api1_internal` for DB_ENV (C++ uses api1, Java
   api2; we take api1 and document it, survey §java). The associate callback is
   stored on the **secondary** DB (its first arg is the secondary — survey §cxx).
2. Install a small `extern "C"` thunk that casts the slot back to the host object
   and invokes it, translating DBTs to slices and the host return to the C int.

Rust specifics: the stashed thing is a `Box<dyn Fn...>` (type-erased), its raw
pointer in `api_internal`, dropped when the handle drops. Comparator closures must
be `'static` (they outlive any call frame) — enforced by the bound. A panic in a
callback must not cross the FFI boundary: wrap the thunk body in
`catch_unwind`, convert a panic to a DB error return.

Zig specifics: the stashed thing is a `*const anyopaque` to a caller struct +
a `*const fn`; the thunk casts back. No unwinding to worry about (Zig has no
exceptions), but a callback that returns an error must map to a C int the C side
understands (e.g. a comparator cannot fail, a secondary extractor returns
`DB_DONOTINDEX` to skip).

The one callback with no public C setter — `DB_DBT_USERCOPY` — is omitted (survey
§5). `set_alloc` is wired implicitly for the MALLOC/REALLOC free path (§5).

## 8. Surface covered in v1 (both languages)

Enough for a real transactional application, matched between the two so docs and
tests are parallel:

- **Env:** create, config builder (cachesize, flags, lock/log/txn tuning, errpfx,
  errcall/msgcall), open, close, `txn_checkpoint`, `failchk` (with the isalive /
  thread_id callbacks), `remove`.
- **Db:** create, config builder (type, pagesize, flags incl. DUP/DUPSORT,
  bt_compare/dup_compare/h_hash callbacks), open (incl. in a txn), `get`/`put`/
  `del`/`exists` in all DBT forms, `cursor`, `associate` + secondary `pget`,
  `sync`, `truncate`, `compact`, `stat`, `close`, `remove`, `rename`.
- **Cursor:** `get` (all op codes: FIRST/LAST/NEXT/PREV/SET/SET_RANGE/GET_BOTH/
  NEXT_DUP/…), `put` (KEYFIRST/KEYLAST/AFTER/BEFORE/CURRENT), `del`, `count`,
  `dup`, `pget`, bulk get as an iterator, close. Modeled as a Rust `Iterator`
  adaptor and a Zig iterator for the common forward/backward scans.
- **Txn:** begin (with parent, flags incl. SNAPSHOT/SERIALIZABLE/NOWAIT),
  commit/abort/discard, `prepare` (XA gid), `id`, `set_name`, `set_timeout`,
  priority; plus the `transact` retry helper (§6).
- **Sequence:** create, open, get(delta), set_cachesize/flags/range, close, remove.
- **Top-level:** `version()`/`full_version()`, `strerror`, a compile-vs-runtime
  version check that errors loudly on header/lib skew (survey §8).

Deferred (Layer 1 reachable, no Layer 2 wrapper in v1): replication/repmgr,
DB_MPOOLFILE, DB_LOGC beyond a thin wrapper, USERCOPY, encryption config beyond a
passphrase setter, the HEAP rid API.

## 9. Documentation — native format per language

The brief asks for getting-started guides, reference manuals and API docs "in the
most suitable format for the language." That differs by language, deliberately:

**Rust.**
- **API docs:** `cargo doc` / rustdoc, generated from doc-comments on every public
  item, with runnable `/// ```` examples that are compiled and run by
  `cargo test --doc` (so the examples cannot rot). This is *the* idiomatic Rust
  reference; it also publishes to docs.rs automatically.
- **Getting started:** `lang/rust/README.md` + a `guide/` of chapter-style
  markdown (open an env, a first put/get, transactions + the retry helper,
  cursors + iteration, secondary indices, bulk ops). Optionally an mdBook if the
  team wants a rendered book, but the doc-comment examples carry most of it.
- **Reference manual:** the rustdoc *is* the reference; a short `MAPPING.md`
  cross-walks every C method to its Rust form (so a BDB C user finds things).

**Zig.**
- **API docs:** Zig's built-in `zig build-obj -femit-docs` / `std` autodoc from
  doc-comments (`///`). Zig's autodoc is young, so the primary reference is
  doc-comments + a hand-written `reference.md` organized like the std docs.
- **Getting started:** `lang/zig/README.md` + `guide/` chapters mirroring the Rust
  ones one-for-one (same examples, Zig idioms: `defer deinit`, error unions,
  allocator passed in).
- **Reference manual + MAPPING.md:** same C-method cross-walk.

Both: a top-level `lang/BINDINGS.md` pointing at both, and each guide's examples
double as the integration tests (§10) so documentation and tests never diverge.

## 10. Tests

Parallel structure, each gated by a `run_*.sh` that emits a VERDICT line (the
house convention — judged on the verdict, not rc) so they slot into the existing
tier/manifest gate.

- **Rust:** `cargo test` (unit + integration under `tests/`), `cargo test --doc`
  (the guide examples), `cargo clippy -D warnings`, `cargo fmt --check`, and
  **Miri** on the pure-Rust logic (DBT iterator arithmetic, error decoding) where
  it doesn't cross FFI. A `tests/` integration suite exercises the real library:
  open/put/get round-trip, txn commit/abort visibility, deadlock-retry, cursor
  scan equals inserted set, secondary index lookup, bulk get equals N single gets,
  USERMEM grow-retry, callback comparator ordering, use-after-close is a compile
  error (a `trybuild` ui test — the type system *is* a test here).
- **Zig:** `zig build test` (Zig's test blocks, same scenarios), run in
  `Debug`+`ReleaseSafe` (so the lifecycle asserts fire) and `ReleaseFast` (so the
  real artifact is exercised). A `std.testing` leak-check on the allocator catches
  a missed `deinit`.
- **Shared teeth:** each binding's drift gate (§3) — a sabotage that bumps a
  constant in Layer 1 must make the gate FAIL; paste the FAIL line in the commit,
  per house rule.
- **Cross-check:** a tiny C program and the two bindings each create a DB, put the
  same keys, and the other two read them back — proving all three agree on the
  on-disk format through the one library.

All of this runs on EC2 FreeBSD (and Linux in CI); never on the maintainer's
workstation.

## 11. Build integration

- **Rust:** a Cargo workspace at `lang/rust/` with `libdb-sys` (Layer 1) and
  `libdb` (Layer 2). `libdb-sys/build.rs` locates `db.h` + the lib: honor
  `DEP_LIBDB_*` / `LIBDB_DIR` env, else `pkg-config`/probe for both `db` and
  `db-2026.0` (survey §8: the autoconf lib is `libdb-2026.0`, a meson build is
  plain `db`). No bindgen at build time if we vendor (recommended §3). Static or
  dynamic link selectable.
- **Zig:** `lang/zig/build.zig` exposing a `libdb` module; it links the system
  `libdb` (or a path given via a build option) and `@cImport`s / uses the vendored
  `c.zig`. `build.zig.zon` for packaging.
- **Autoconf/meson:** the bindings are *optional* and *out-of-tree-buildable* —
  they consume an installed libdb, so they need no hook in `dist/configure` for
  v1 (a user runs `cargo build` / `zig build` against an installed lib). A later
  `--enable-rust`/`--enable-zig` can drive them from the main build if wanted;
  deliberately deferred so the bindings don't entangle the C build system.
- **No change to the C library, the soname, or any format.** The bindings are
  pure consumers. The region/ABI freeze of the LTS line is untouched.

## 12. Risks and how each is handled

- **Header/lib skew** (survey flagged `build_unix` was 2026.10.1 vs HEAD 2026.10.7):
  the compile-time-vs-runtime version check (§8) + the drift gate (§3) catch a
  binding built against the wrong header. All ABI facts in this RFC were
  re-measured on a HEAD build.
- **DBT lifetime foot-guns** (DB-owned pointer valid only to the next op): the
  default output form copies out (safe); the zero-copy form is a borrowed closure
  (Rust: lifetime-bounded) / a documented-window slice (Zig). The dangerous form
  is never the default.
- **Callback panics / errors crossing FFI:** Rust `catch_unwind` in every thunk;
  Zig callbacks return a C int, cannot unwind.
- **Thread-safety mismatch:** `Send`/`Sync` gated on `DB_THREAD` (Rust);
  asserted + documented (Zig). The non-free-threaded handles are `!Sync`.
- **Reproducible builds:** Layer 1 vendored + regenerated by a committed script,
  not generated at build time (§3).

## 13. Plan (phases, each independently shippable, each on EC2 FreeBSD + Linux CI)

- **Phase 0 — Layer 1 for both** (`libdb-sys`, `c.zig`): opaque handles,
  constants, DBT, method-pointer signatures; the drift gate with teeth. Smallest
  thing that links and calls `db_version()`.
- **Phase 1 — Core data path:** Env + Db open/close, `get`/`put`/`del`/`exists`
  (all DBT forms), the error model, the version check. Getting-started guide
  chapter 1–2. Round-trip + USERMEM tests.
- **Phase 2 — Transactions + cursors:** Txn + the `transact` retry helper,
  Cursor + iteration, deadlock retry. Guide chapters 3–4. Txn-visibility,
  cursor-scan, deadlock tests; the Rust `trybuild` use-after-close test.
- **Phase 3 — Callbacks + secondary indices + sequences + bulk:** the trampoline,
  `associate`/`pget`, comparators, `DB_MULTIPLE_*` iterators, Sequence. Guide
  chapters 5–7. Comparator-ordering, secondary-lookup, bulk-equivalence tests.
- **Phase 4 — Docs + polish:** rustdoc/autodoc complete, reference + MAPPING.md,
  `lang/BINDINGS.md`, the cross-language on-disk cross-check test, CI wiring
  (`run_rust.sh`, `run_zig.sh` verdict gates).

Each phase: worker implements → independent reviewer verifies on a fresh FreeBSD
host (builds, runs the tier, rebuilds every sabotage arm) → lead integrates. No
phase lands without its drift gate and its guide examples compiling as tests.

## 14. Decisions requested

1. **Layer 1: generated-then-vendored (recommended) vs hand-written** (§3).
2. **Rust thread model: always-require-`DB_THREAD` for the safe sharable API
   (simpler v1) vs two handle types `Db`/`DbLocal`** (§4).
3. **Zig version to pin** (0.16.0 is installed on the dev host; Zig moves fast —
   pin one and state the support policy).
4. **Rendered book (mdBook / Zig site) vs doc-comments-only** for the guides (§9).
5. **v1 surface line** — is §8 the right cut, or should any deferred item
   (encryption passphrase? DB_LOGC?) move into v1?
