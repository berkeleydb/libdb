# P13 / P12 four-arm matrix — measurement, correctness gates, deployability

**Status of the numbers below:** every figure is recomputed from
`test/bench/P13-P12-MATRIX-2026-10.tsv` and `test/bench/P13-P12-MATRIX-2026-10-confirm.tsv` by
`test/bench/P13-P12-MATRIX-2026-10-tools/an.py`, `sig.py` and `pc.py`, and every gate verdict comes
from a command run on the measurement host during this session. Three
predictions in the brief did not survive checking and are corrected in place,
each with its working shown (§2 the stripe size, §7 the SKIP accounting,
§9 what P13 alone is worth).

---

## 1. Headline

**P12 alone is a regression. P12 on top of P13 is a win. The ordering was the
whole problem.**

| | t=16 | t=32 | t=64 |
|:--|--:|--:|--:|
| P12 alone, vs base | −13.7% | −19.6% | −18.3% |
| P12 on top of P13, vs P13 | **+28.8%** | **+22.3%** | **+12.0%** |

RFC 0012 described P12's latch as "incidental admission control". That reading
was right about the mechanism and wrong about the sequence: P12's per-stripe
locker allocation removes locker-allocation waits either way, but **without P13
it redirects the pressure onto `MUTEX_SYSTEM_LOCK`**, and the mutex-region wait
it creates there costs more than the locker wait it saves. P13 removes that
bottleneck first, so P12's saving is kept instead of spent. Evidence in §5.

**The catch, which is a product decision and not a technical one:** P13+P12
**moves the region signature**, so every existing environment must be
recreated. P13 alone does not. Both numbers side by side in §8.

## 2. What was measured, and the one correction to the brief's arithmetic

Host: `i-07ec57a8e86f2c3cf`, **c6id.16xlarge**, 64 vCPU Intel Xeon Platinum
8375C @ 2.90 GHz, `us-east-2c`, Linux 6.1.0-53-cloud-amd64, `/nvme` XFS
(`rw,relatime,attr2,inode64,logbufs=8,logbsize=32k,noquota`), THP `[never]`,
no cpufreq governor exposed, load average 0.03 at the time of the gate runs.
gcc 12.2.0, Tcl 8.6.13.

Driver `xe_tproc_c` (TPROC-C-like), scale 96, pad 256, 4 GiB cache, 20 s
measured after 8 s warmup, 9 reps per cell, arms alternating within each rep
with a rotating start arm.

**One binary, four arms selected by environment variable.** The sweep did not
use the four build trees; it used the P13+P12 build, which carries both
runtime switches, with arms selected as:

| arm | environment |
|:--|:--|
| base | `DB_NO_LOCKER_SHARD=1 DB_NO_LOCKER_MUTEX_REUSE=1` |
| P13 | `DB_NO_LOCKER_SHARD=1` |
| P12 | `DB_NO_LOCKER_MUTEX_REUSE=1` |
| P13+P12 | neither set |

This is the right call and I verified the hazard it avoids is actually handled:
`locker_shard` is read **once at region creation** and stored in the region, so
setting `DB_NO_LOCKER_SHARD` on a run that *attaches* an existing region is
silently ignored. `p13mx.sh` recreates the environment for every single run
(`find "$DATA" -mindepth 1 -delete` then a fresh load under the same arm env).
A previous pass that reused one dataset across arms fabricated a 13×
regression from exactly this.

### Correction: the stripe is 64 bytes, not 40, so the region grows to 5064

The brief predicted `DB_LOCKREGION` 1000 → 3528 bytes. **Measured: 1000 →
5064.** 3528 is the *pre-padding* figure. Compiled in-tree
(`test/bench/P13-P12-MATRIX-2026-10-tools/sz2.c`):

```
t_base      sizeof(DB_LOCKREGION)=1000
t_P12P13    sizeof(DB_LOCKREGION)=5064
            sizeof(DB_LOCKERSTRIPE)=64   LOCK_LOCKER_STRIPES=64
            stripe_array_bytes=4096
            region_minus_stripe_array=968
            hypothetical_if_stripe_were_40B=3528   <-- the brief's number
```

`DB_LOCKERSTRIPE`'s four real fields are 40 bytes (2 × `SH_TAILQ_HEAD` + 2 ×
`u_int32_t`), and the struct carries an explicit `u_int8_t pad[24]` to fill a
cache line, enforced by a negative-width-bitfield build assert at
`src/dbinc/lock.h:166-169`. So 968 + 64×64 = **5064**, and 968 + 40×64 = 3528
is what a 40-byte stripe would have given. The deployability conclusion is
unchanged and marginally larger: the lock region grows **4064 bytes**, not 2528.

## 7. Correctness gates

Both configurations built from a build directory that is a **sibling** of the
source tree, as required:

- **`gP`** — default build: `../src/dist/configure --enable-tcl
  --with-tcl=/usr/lib/tcl8.6 --enable-stl`, `make -j32` rc=0.
  `db_config.h` has **no** `DIAGNOSTIC` define (verified).
- **`gPd`** — `../src/dist/configure --enable-diagnostic --enable-tcl
  --with-tcl=/usr/lib/tcl8.6`, `make -j32` rc=0.
  `db_config.h` has `#define DIAGNOSTIC 1` (verified — I checked rather than
  trusting the configure flag).
- **`tP` / `tPd`** — the same two, plus `--enable-test`, needed because the TCL
  suite is not built otherwise.

The sibling layout matters: three runners (`run_handle_sizes`,
`run_s5_failchk_spin`, `run_opt_null_sample`) resolve `BUILD` as
`$HERE/../../build_unix` rather than honouring `BUILD=.`, so in a sibling
layout they look inside the *source* tree and report `FAIL no libdb library`.
A `build_unix -> ../bld` symlink in each gate tree resolves it. This is why the
earlier `/nvme/gate` run showed 3 FAILs; those were a harness-layout artifact,
not a defect in the arm.

### Correction: the SKIP accounting is three-and-absent, not two

The brief expected two SKIPs (JNI absent; `run_mvcc_mtx_doublefree`). Measured:

**Three internal SKIPs**, all environmental, identical on both builds:

| runner | reason |
|:--|:--|
| `run_u9_serializable` | `SKIP no javac on this host` (the JNI one) |
| `run_u8_backup_config` | `SKIP no javac on this host` (also JNI) |
| `run_meson_autoconf_parity` | `SKIP no meson on this host` — `which meson` returns nothing on this Debian box |

Note these still emit `pass` verdicts to `db.results` (the runners treat an
unavailable toolchain as a pass-with-skip-notice), which is why the table above
reads 19/19.

**And `run_mvcc_mtx_doublefree` is *absent*, not skipped.** It is not in the
`test/MANIFEST` of the trees under test, so `run_all.sh` — which reads its list
from the manifest — never invokes it. The db tier has 19 entries and that is
not one of them. Cause: the gate trees derive from commit `e4281be0c`, and
`run_mvcc_mtx_doublefree` (plus the F6 `__mutex_free` guard it exercises)
arrived in `b027cd36f`, one commit later. I verified the trees' provenance

## 8. Region signature — the deployability crux

`__env_struct_sig()` via `BUILD_DIR=<dir> bash dist/env_sig_print.sh`,
confirmed rather than assumed:

| arm | `__env_struct_sig()` | `sizeof(DB_LOCKREGION)` | moved? |
|:--|:--|--:|:-:|
| base | `0xb86f77f0` | 1000 | — |
| **P13** | **`0xb86f77f0`** | 1000 | **no — identical to base** |
| P12 | `0x0b67cec8` | 5064 | **yes** |
| P13+P12 | `0x0b67cec8` | 5064 | **yes** |

Exactly as predicted (apart from the 3528→5064 correction in §2). P13 adds no
shared state. P12 embeds `locker_stripe[64]` in `DB_LOCKREGION`, and
`env_sig.c` hashes `sizeof()` of every shared struct, so the signature moves.

### I did not stop at the hash — I verified the user-visible consequence

`env_region.c` refuses to attach when `renv->signature != __env_struct_sig()`.
A cross-attach probe (`test/bench/P13-P12-MATRIX-2026-10-tools/xa.c`: create with one arm's binary,
attach with another's, no `DB_CREATE`):

**Environment created by `base`:**

| attaching binary | result |
|:--|:--|
| base | `open rc=0 (success)` |
| **P13** | **`open rc=0 (success)`** |
| P12 | `BDB1539 Build signature doesn't match environment` → `rc=-30969 DB_VERSION_MISMATCH` |
| P13+P12 | `BDB1539` → `rc=-30969 DB_VERSION_MISMATCH` |

**Environment created by `P13+P12`:**

| attaching binary | result |
|:--|:--|
| base | `BDB1539` → `rc=-30969 DB_VERSION_MISMATCH` |
| P13 | `BDB1539` → `rc=-30969 DB_VERSION_MISMATCH` |
| P12 | `open rc=0 (success)` |
| P13+P12 | `open rc=0 (success)` |

The break is **bidirectional**: a P13+P12 binary cannot read an old
environment, and an old binary cannot read a P13+P12 one. No rollback path
without recreating the environment in either direction.

### And the off-switch does not rescue it

| attempt | result |
|:--|:--|
| P13+P12 binary + `DB_NO_LOCKER_SHARD=1`, attaching a base env | `rc=-30969 DB_VERSION_MISMATCH` |
| P13+P12 binary + both switches off, attaching a base env | `rc=-30969 DB_VERSION_MISMATCH` |
| `__env_struct_sig()` with `DB_NO_LOCKER_SHARD=1` | `0x0b67cec8` — **unchanged** |

**The region-format break is unconditional, not opt-in.** `DB_NO_LOCKER_SHARD`
disables the *algorithm*; it cannot disable the *layout*, because the signature
is a compile-time property of the struct and the field is present regardless.
A deployment that ships the P12 binary has taken the break whether or not it
uses the feature.

### The trade-off, stated as a trade-off

Two different products. The maintainer picks; this is not a recommendation.

| | **P13 alone** | **P13 + P12** |
|:--|:--|:--|
| Linux throughput, t=32 | −0.3% (not significant, §9) | **+22.0%** (p=0.00004) |
| Linux throughput, t=16 / t=64 | +6.8% / −1.5% (neither significant) | **+37.6% / +10.3%** |
| FreeBSD | the ~1500× fix — P13's actual justification | same |
| Region signature | **`0xb86f77f0`, unchanged** | **`0x0b67cec8`, moved** |
| Existing environments | **attach cleanly, verified** | **`DB_VERSION_MISMATCH`, verified both directions** |
| Upgrade procedure | drop-in | **every environment must be recreated** |
| Rollback | drop-in | also requires recreation |
| Can the switch avoid the break? | n/a | **no — layout is unconditional** |
| Correctness gates | not separately gated here (§11) | **all clean, both builds, all 4 switch positions** |
| Scale-shape gate | still FAIL | still FAIL, but best of four (§10) |

"**+22% but a region-format break**" and "**~0% and transparent**" are the two
options. The abi-drift gate cannot see this difference: the public ABI
(`sizeof(DB)`, `DBC`, `DB_ENV`, `DB_TXN`) is unchanged, so `abidiff` goes
green while real customer upgrades fail — the hazard `dist/env_sig_print.sh`
exists to catch, and which nearly shipped in v2026.09.5.

## 9. P13 alone on Linux: ~0%, and not inflated

**P13 alone is a no-op on Linux throughput.** Range across thread counts
−1.5% to +6.8%, and — the part worth stating plainly — **not a single P13-alone
cell is statistically significant**, including the +6.8% at t=16:

| t | P13 vs base | exact p | verdict |
|---:|--:|--:|:--|
| 1 | +0.1% | 0.931 | not significant |
| 2 | −0.0% | 0.796 | not significant |
| 8 | +0.1% | 0.863 | not significant |
| 16 | **+6.8%** | **0.094** | **not significant** |
| 32 | −0.3% | 0.489 | not significant |
| 64 | −1.5% | 0.605 | not significant |

The brief said "all but one cell within noise"; the exact test says **all six**
are, with the t=16 cell at p=0.094 — suggestive, short of α=0.05, and not
something to quote as a gain.

**P13's justification is the FreeBSD ~1500× fix, not Linux throughput.** On
Linux it is a **no-cost no-op that unblocks P12**, and that is its entire Linux
value proposition: it adds no shared state, does not move the region signature,
attaches existing environments cleanly (§8), costs nothing measurable, and
converts P12 from a −19.6% regression into a +22.0% gain. That is worth
shipping on its own terms. It is not a Linux performance win and should not be
presented as one.

## 11. What I did NOT verify

Explicitly, so nothing here is mistaken for a stronger claim than it is.

**Re-measurement**
1. I did not re-run the sweep. Every number in §3–§6 and §10 is a recomputation
   of the existing TSVs, not a fresh measurement. I verified the TSVs are
   complete (24 cells × 9 reps, zero `LOAD_FAILED`/`TIMEOUT_STALL`/`NO_VERDICT`
   rows) and that `t_base` matches local `e4281be0c` byte-for-byte, but I did
   not independently reproduce any throughput figure.
2. The confirm sweep's P12/t=64 and P13P12/t=64 cells have **4 reps, not 5**. I
   did not top them up. Those two deltas rest on 4 samples.
3. No profiling. I did not confirm by `perf` or any profiler that
   `MUTEX_SYSTEM_LOCK` is the specific contended object; that attribution rests
   on the `x_region` counter and the §6 probe, which are consistent with it but
   are counters, not stacks.

**Correctness coverage**
4. **The F6 / `run_mvcc_mtx_doublefree` arm is NOT covered.** It SKIPs on both
   builds (0 reclaimed mutexes, scenario never constructed) and I am reporting
   that as proving nothing. The double-free hazard is unexercised here.
5. **The gate trees are one commit behind local HEAD** (`e4281be0c`, HEAD is
   `b027cd36f`). The F6 `__mutex_free` guard is not in the measured or gated
   code except in the standalone run of §7. The combination "P13+P12 on top of
   `b027cd36f`" has **not** been gated.
6. **I gated only the P13+P12 arm.** `run_all.sh`, `lockmatrix`, the TCL
   lock/dead tests and `s5_failchk_spin` were run against the P13+P12 tree
   only. base, P13-alone and P12-alone got `s_validate` and `s_execbits` but
   **not** the functional tiers. So "P13 alone ships without breaking existing
   environments" is backed by the signature and cross-attach evidence in §8,
   **not** by a correctness run of the P13-alone build. If P13 alone is the
   shipping candidate, it needs its own gate pass.
7. No sanitizer builds: no ASan, no TSan, no UBSan, no LeakSanitizer in any
   arm. Given that the whole point of P12 is to change which threads touch
   which shared state, **a TSan run is the obvious missing gate** and its
   absence is the largest hole in §7.
8. Not run: the 32-bit build, macOS, FreeBSD, the `meson` parity check (no
   meson on the host), the JNI/Java tiers (no javac), the full TCL suite
   beyond the 13 lock/dead tests, the soak and leak tiers, `run_handle_sizes`
   against a release tag, and `abidiff`.
9. One platform only: 64 vCPU Intel on Linux 6.1. No NUMA-spanning host, no
    AMD, no ARM. P13's FreeBSD ~1500× claim is **inherited from prior work and
    was not re-verified in this session** — no FreeBSD machine was involved.
10. Only `lk_partitions` 1 and 10 (what `run_s5_failchk_spin.sh` drives), and
    only `LOCK_LOCKER_STRIPES=64`. No sensitivity analysis on stripe count,
    and in particular no check of what happens when stripes ≫ cores or on a
    machine where 64 stripes × 64 B interacts differently with the cache.
11. Durability modes other than the driver's default were not varied, and I did
    not vary scale beyond the 96 of the main sweep and the {32, 96} of the
    shape gates.

**Not done, by instruction**
12. Nothing was committed and nothing was pushed. No benchmarks were run on
    `floki`; all measurement and gating happened on the EC2 host.
