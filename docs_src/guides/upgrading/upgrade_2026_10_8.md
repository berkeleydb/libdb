## Upgrading to libdb 2026.10.8

libdb 2026.10.8 is a regular release from `master`. It follows the 2026.10.7 LTS release.

**No upgrade procedure is needed.** The shared-memory region format, the database and log formats, the soname (`libdb-2026.0`) and the public ABI of a default build are the same as 2026.10.7. An environment created by 2026.10.7 or 2026.10.7.1 opens with 2026.10.8 and the other way round, and processes from these releases can share one environment.

### Faster transactional writes

A cross-release benchmark (`test/bench/XREL-2026-10.md`) found that transactional inserts and updates had become slower than in Berkeley DB 5.3.28, while reads had become much faster. Two causes are fixed in this release (#228). The scalability changes that caused them are kept.

- **The deadlock detector skips its graph when no deadlock is possible.** With detection on every lock conflict, the default for `DB_LOCK_DEFAULT` with `set_lk_detect`, each thread that blocks runs the detector before it sleeps. Each run took all 64 locker-table mutexes and walked every locker, even though nearly every conflict is a queue of threads behind one busy page, which cannot deadlock. The detector now checks the objects with waiters first. When every waiter is on one object and none is waiting to upgrade a lock it already holds, it skips the graph. Aborting a deadlock victim now locks only the victim's part of the locker table.
- **Inserts and deletes stop locking idle cursor queues.** Each database handle keeps its open cursors in 8 queues so that concurrent readers do not contend. An insert or delete must adjust any cursor positioned near the change, and it locked all 8 queues to look. It now skips a queue that has no cursors, without locking it.

Measured against 2026.10.7 with transactional `xrel_kv` (YCSB-style), detection on every conflict, median of 3 runs. Every quoted cell has CV ≤ 10.7%:

| Transactional workload | Linux x86_64 (c6id.metal) | Linux aarch64 (c7gd.metal) | FreeBSD aarch64 (c7g.metal) |
| --- | --- | --- | --- |
| Btree insert, 1 thread | 1.13× | 1.08× | 1.04× |
| Btree insert, 4 threads | 1.43× | 1.65× | 1.50× |
| Hash insert, 16 threads | 1.49× | 2.34× | 1.05× |
| Recno read-modify-write, 4 threads | 1.88× | 2.47× | 2.38× |
| Recno insert, 4 threads | 1.64× | 1.87× | — |
| Btree read, 16 threads | 0.96× | 0.97× | 1.07× |

On Btree, Hash, Queue and Heap, reads, scans and updates are unchanged: 0.95–1.10× across 62 Linux x86_64 cells. Mixed Recno workloads gain 1.0–1.7×, because their updates hit the same detector cost. Recno inserts and updates are still slower than 5.3.28 at 16 or more threads, and so are Btree inserts at 16 threads, where every thread appends to the same last page. See `test/bench/XREL-2026-10.md` for the full table.

If your application runs the deadlock detector from a timer (`DB_ENV->lock_detect` or `db_deadlock`) instead of on every conflict, it saw less of the old cost, so it gains less.

### Also in this release (since 2026.10.7)

- **Typed data and constraints (RFC 0014)**, opt-in with `--enable-typed`. A Btree or Hash subdatabase can declare record and field codecs, and libdb enforces NOT NULL, MAXLEN, VALID and UNIQUE on every put. A default build does not compile the layer, its library is byte-identical to one built without it, and its region signature is unchanged. A default or older library refuses to open a typed subdatabase with `EINVAL`.
- **Rust and Zig bindings (RFC 0016)** under `lang/rust` and `lang/zig`.
- **DTrace and USDT probes** for the log fsync and the asynchronous checkpoint page write.
- The three fixes of 2026.10.7.1: reverse cursor walks (`DB_PREV`) that could skip records under clang on aarch64, `DB_TRUNCATE` with a subdatabase name (now refused with `EINVAL`), and a lock-order inversion when discarding a written file from the cache. See [Upgrading to libdb 2026.10.7.1](upgrade_2026_10_7_1.md).
- The nightly configure-option gate sweeps `--enable-typed`.

### Known issues

- **`configure` cannot guess the build type on Linux aarch64.** The bundled `dist/config.guess` dates from 2011 and does not recognise `aarch64-*-linux`. Every release since Berkeley DB 5.3 has it. Pass the triplet explicitly: `../dist/configure --build=aarch64-unknown-linux-gnu`. FreeBSD aarch64 and macOS arm64 are not affected.
- **macOS arm64: two processes contending on one environment can panic** (`pthread suspend failed`, then `BDB0061 PANIC: Invalid argument` and `DB_RUNRECOVERY`). Darwin's process-shared condition variable records the address at which the creating process mapped the region, and a second process maps it elsewhere. It is in the hybrid mutex's blocking path, which 2026.10.7 made the default on macOS arm64. Configuring with `--with-mutex=POSIX/pthreads/library` avoids it. A fix is in review (#226). Use from a single process, including many threads, is not affected.
