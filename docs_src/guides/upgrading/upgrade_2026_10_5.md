## Upgrading to libdb 2026.10.5

**libdb 2026.10.5 changes the shared-memory environment region format.** Databases and log files do not change. Only the region files (`__db.001`, `__db.002`, …, or the equivalent shared memory segments) are affected, and libdb recreates them from scratch whenever an environment is opened after it has been removed.

This is the first release of the fork to change the region format. No release has been designated long-term support, and this change was made deliberately in exchange for a large multi-core throughput gain (below).

### What changed and why

The lock region's locker allocation used to be serialised by a single latch. libdb 2026.10.5 gives each of the 64 locker stripes its own free list, counters and list of lockers (P12). Locker-allocation latch waits fall 10–140×, and transactional throughput on a 64-core Linux machine rises **+12% to +29%** between 16 and 64 threads compared with 2026.10.4. This depends on the change that shipped in 2026.10.4 to stop freeing and reallocating a locker's mutex on every transaction (P13). Without it, the same per-stripe change *loses* 18–20%, which is why it was held back until now.

The new per-stripe state lives in the shared lock region (`DB_LOCKREGION` grows from 1,000 to 5,064 bytes on LP64), so the environment's build signature changes.

### What you will see if you do not follow the procedure

A 2026.10.5 process that opens an environment created by 2026.10.4 or earlier, or the other way round, fails cleanly:

    BDB1539 Build signature doesn't match environment
    DB_ENV->open: DB_VERSION_MISMATCH

Nothing is read or written in that case. Mixed-version processes can never share one region. That includes a 2026.10.5 process and a 2026.10.4 utility such as `db_stat` or `db_recover`.

### Procedure

This is the standard procedure for a release that changes regions but not log or database formats. It is the third case in [Upgrading Berkeley DB installations](upgrade_process.md).

1. Shut down every process using the environment, including utilities.
2. **Still using the old version**, run recovery: `db_recover -h <home>`, or open the environment with `DB_RECOVER`.
3. Remove the environment's regions: `DB_ENV->remove()`, or delete the `__db.0*` files in the environment home. **Never delete log files or databases.**
4. Install 2026.10.5. Relink or rebuild everything that uses the library, including any utilities you ship.
5. Restart. The first open creates fresh regions in the new format.

A non-transactional environment can skip step 2.

There is no database or log upgrade step, and `db_upgrade` is not needed.

### Turning the new behaviour off does not restore compatibility

`DB_NO_LOCKER_SHARD=1` disables the per-stripe *algorithm* at runtime. It does not change the region *layout*, which is fixed at compile time. A 2026.10.5 binary with the switch set still cannot attach a 2026.10.4 environment. The switch exists for diagnosis and A/B measurement, not for compatibility.
