# P4 — `__db_walk_cursors` holds `env->mtx_dblist` across the whole cursor walk

Branch `fix/p4-cursor-walk-lock`. Commit: *fix(db): repair the cursor-walk
retry protocol; take mtx_dblist shared*.

**Outcome, stated plainly.** Two things came out of this, and only one of them
is the thing I was sent to do.

1. **A correctness bug, fixed and proven in both directions.** The
   `DB_LOCK_NOTGRANTED` retry protocol I was told to "keep correct" was already
   broken on master, and had been since the cursor queues were sharded. Against
   unfixed master the new regression test **hangs**; with the fix it passes.
   This is independent of P4 and can be cherry-picked alone.

2. **P4 itself: a NULL result on throughput.** The global lock is real and the
   fix removes it from the profile — `__bam_ca_di` falls from **30.74% to 2.89%**
   of all time at t=64 — but throughput does **not** improve. Every thread count
   lands inside the noise floor except t=64, which **regresses ~9.5%**. The
   shape still peaks at t=2. `mtx_dblist` was not the binding constraint on this
   workload; `__log_put` is, at **56%** of all time. I kept the change because
   it is correct and measured, not because it was shown to pay.

The brief said a reasoned negative result is a valid outcome. On the performance
question this is one, and section 6 explains exactly why, with the mechanism
measured rather than guessed.

---

## 1. What the defect was

`src/db/db.c:1381` took `env->mtx_dblist` **exclusively** and held it across the
entire walk:

```c
MUTEX_LOCK(env, env->mtx_dblist);          /* environment-wide, exclusive */
FIND_FIRST_DB_MATCH(env, dbp, ldbp);
for (...; ldbp = TAILQ_NEXT(ldbp, dblistlinks)) {
    for (cq_i = 0; cq_i < DB_CURSOR_NPART; cq_i++) {
loop:   CQ_LOCK(env, cqp);                 /* inside the global one */
        TAILQ_FOREACH(dbc, &cqp->active_queue, links) ... func(dbc, ...) ...
```

The queues are sharded 8 ways with their own `CQ_LOCK`, but since the global
latch is taken first and held throughout, the sharding bought nothing for this
path. `__bam_iitem → __bam_ca_di → __db_walk_cursors` runs on every insert.

The brief's diagnosis was correct and I did not re-derive it. What I did check
is the claim underneath it — that the latch guards only the handle list — and
that check is what section 3 is.

## 2. Approach taken, and why

The brief ranked three options and preferred (1): snapshot the handle list,
drop the latch, walk the partitions. I took a **cheaper variant of (1) that
makes the lifetime question disappear instead of answering it**: keep holding
the latch for the whole walk, but hold it **shared**.

```c
MUTEX_READLOCK(env, env->mtx_dblist);      /* readers run concurrently */
```

and allocate it as a shared latch (`src/env/env_open.c`):

```c
if ((ret = __mutex_alloc(env, MTX_ENV_DBLIST,
    DB_MUTEX_PROCESS_ONLY | DB_MUTEX_SHARED, &env->mtx_dblist)) != 0)
```

Why this rather than the snapshot:

- **It is strictly less code.** Four call sites and one allocation flag, no
  snapshot buffer, no allocation on the insert path, no error path for a failed
  allocation on the hottest path in the library.
- **It removes the serialization just as completely.** Concurrent inserts are
  all readers, so they no longer exclude each other. That is the entire content
  of P4.
- **It does not create a lifetime problem, so there is none to argue away.**
  The snapshot approach drops the latch and then dereferences handle pointers
  taken under it — that is where use-after-free risk comes from. Holding the
  latch shared never lets go, so a handle cannot be unlinked while the walk is
  in progress. See section 3.
- **The machinery already exists and is load-bearing elsewhere.**
  `DB_MUTEX_SHARED` / `MUTEX_READLOCK` is what mpool uses for `hp->mtx_hash`
  and `bhp->mtx_buf`. No new primitive.

Option (2) (a per-handle cursor count) I did not pursue: it needs state in
`struct __db`, which `env_sig.c` hashes, and the brief is explicit that
`sizeof(DB)` must stay 1744 and the signature must not move. Option (3) was
gated on 1 and 2 failing.

## 3. Handle-lifetime safety argument

**Claim.** No handle reachable from the walk can be freed, or unlinked from
`dblist`, while the walk holds `mtx_dblist` shared.

**Every acquisition of the latch in the tree** (`grep`, whole source):

| Site | Mode | What it does |
|---|---|---|
| `db.c:538` (`__env_setup`) | **exclusive** | `TAILQ_INSERT_HEAD`/`INSERT_AFTER` — mutates the list |
| `db.c:964`–`1066` (`__db_refresh`) | **exclusive** | `TAILQ_REMOVE` — unlinks the handle |
| `db.c:784` (`__db_close`) | **exclusive** | `--env->db_ref` |
| `db_method.c:178` (`db_create`) | **exclusive** | `++env->db_ref` |
| `db.c:1401` (`__db_walk_cursors`) | **shared** | reads `dblistlinks`, runs the callback |

The walk is the **only** reader. Every mutator is exclusive. A reader/writer
latch guarantees no writer overlaps a reader, so for the whole duration of the
walk:

1. **The list shape is stable.** `FIND_FIRST_DB_MATCH` walks `TAILQ_PREV` and
   the loop walks `TAILQ_NEXT`. Both only need the links to be immutable, which
   exclusion against `TAILQ_INSERT_*`/`TAILQ_REMOVE` provides.
2. **No handle is freed.** The free is `__os_free(env, dbp)` in `__db_close`
   (`db.c:~790`), and it is *after* `__db_refresh` has taken the latch
   exclusively to unlink the handle. A handle therefore cannot reach
   `__os_free` without first completing an exclusive acquisition, which cannot
   happen while we hold it shared. So a handle the walk can see is a handle
   that has not yet been unlinked, hence not yet freed.
3. **`cq_parts[]` stays valid.** The partition mutexes are freed in
   `__db_refresh` (`db.c:1188`), on the same path, after the same exclusive
   acquisition — inside the same critical section that unlinks the handle.
   `memset(dbp, CLEAR_BYTE, ...)` likewise.

**Why this is the stronger argument, not a dodge.** Under the snapshot design
the obligation is "prove each snapshotted pointer stays alive after the latch
is dropped", and answering it needs a pin (`refcount`, open-handle count)
that does not currently exist — the brief anticipated this and said to say so
if a handle can vanish. Holding the latch shared discharges the obligation
structurally: the window in which a pointer could go stale is never opened.
The cost is that a handle open/close blocks for the duration of a cursor walk,
which is what the exclusive version already did to *every* insert.

**One thing I verified rather than assumed:** that the callback cannot
re-enter the latch. A recursive acquisition of a non-recursive latch
self-deadlocks, and read-locking does not make it recursive (a second reader on
the same thread can deadlock behind a queued writer). The table above is the
proof — `db.c:1401` is the only site in `__db_walk_cursors`'s reachable
callback set, and none of the three mutating sites is reachable from a cursor
adjustment callback. The DIAGNOSTIC same-latch checker (`mut_order.c`, which
flags "same latch acquired twice by one thread" independent of rank) ran the
full isolation tier and both cursor suites without firing — section 5.

## 4. The `DB_LOCK_NOTGRANTED` retry protocol — a pre-existing bug

This is the part that was already broken, and it is the more serious finding.

**The protocol.** Three callbacks cannot finish while the queue mutex is held,
because they call back into cursor alloc/free, which takes that same mutex.
Such a callback drops the mutex, does its work, and returns
`DB_LOCK_NOTGRANTED` meaning "I released it, rescan from the top".

**What broke it.** `f9937fab5` (the cursor-shard commit) changed the walk from
holding `ldbp->mutex` to holding `cq_parts[i].mutex`:

```c
/* before f9937fab5 */        /* after f9937fab5 */
loop: MUTEX_LOCK(ldbp->mutex) loop: CQ_LOCK(env, cqp)
```

but left all three callbacks dropping `dbp->mutex` — the mutex the walk held
**before** sharding and has not held since:

| Callback | Drops (wrong) | Then calls | Which takes |
|---|---|---|---|
| `bt_curadj.c:360` `__bam_ca_dup_func` | `dbp->mutex` | `__bam_opd_cursor` | `__db_cursor_int` → `CQ_LOCK` |
| `bt_curadj.c:447` `__bam_ca_undodup_func` | `dbp->mutex` | `__dbc_close` | `CQ_LOCK(DB_CURSOR_PART(dbc))` |
| `hash_rec.c:1524` `__ham_chgpg_recover_func` | `dbp->mutex` | `__dbc_close` | `CQ_LOCK(DB_CURSOR_PART(dbc))` |

On a `DB_THREAD` handle that is two defects at once:

1. **Unlocking a mutex the thread does not hold.** `dbp->mutex` is a live,
   allocated mutex; the walk simply is not holding it. Under DIAGNOSTIC the
   pthread layer panics (`"unlock %ld already unlocked"`,
   `mut_tas.c` / `mut_pthread.c:645`). In production, `pthread_mutex_unlock` of
   an unheld NORMAL-type mutex is undefined and can leave two threads believing
   they hold it.
2. **Self-deadlock.** The partition mutex stays held across a call that
   re-acquires it. Non-recursive, so it never returns.

**Why it shipped green.** Both `dbp->mutex` and `cq_parts[].mutex` are
allocated *only* under `DB_THREAD` (`db.c:497` and `db.c:508`). Without
`DB_THREAD` both are `MUTEX_INVALID`, and `CQ_LOCK`/`MUTEX_UNLOCK` are no-ops —
so both defects vanish. The TCL cursor suites use non-threaded handles.

**I proved that, rather than asserting it.** I built an instrumented library
counting entries to the retry path and ran all eight cursor tests × two
methods:

```
recd013, test048, test053, test072, test073, test086, test087, test088
  × {btree, hash}  ->  16/16 OK,  retry-path hits = 0
```

**Zero.** Those suites never execute this code. Passing them says nothing about
this protocol — exactly the vacuous-green the brief warned about. (My first
attempt to read that counter was itself broken: I read it under gdb *after*
process exit, which reads the ELF image and always says 0. Re-measured
in-process, it reports real hits. A broken probe looks exactly like absent
behavior.)

**The fix.** Drop and retake the mutex the walk actually holds:

```c
cqp = DB_CURSOR_PART(dbc);
CQ_UNLOCK(dbp->env, cqp);
if ((ret = __bam_opd_cursor(dbp, dbc, args->first, args->tpgno, args->ti)) != 0) {
        CQ_LOCK(dbp->env, cqp);
        return (ret);
}
```

`DB_CURSOR_PART(dbc)` is exactly the partition being walked: `dbc` came from
`cqp->active_queue`, and `dbc->part` is assigned at allocation and never
changes (`db.in:2057`, `db_am.c:160`), so `&dbc->dbp->cq_parts[dbc->part] == cqp`.

On the error path the callback retakes the mutex and returns the error, because
the walk's `if (ret != 0) break` path falls through to `CQ_UNLOCK` and would
otherwise unlock an unheld mutex. On the success path it stays unlocked and
returns `DB_LOCK_NOTGRANTED`, and the walk re-locks at `loop:`.

**A third bug, on the same lines.** The walk did:

```c
if (ret == DB_LOCK_NOTGRANTED)
        goto loop;              /* ret still == DB_LOCK_NOTGRANTED */
```

`ret` keeps that value across the jump. If the rescan completes without the
callback firing again, `TAILQ_FOREACH` leaves `ret` untouched and the stale
`DB_LOCK_NOTGRANTED` is returned to the caller **as a real error** —
surfacing out of `__bam_dup_convert` as a spurious failure from an insert that
succeeded. Now reset to 0 before rescanning. (Latent on master for the same
`DB_THREAD` reason.)

**Proof in both directions**, which is the only kind that counts for a hang:

```
FIX  arm: PASS curadj_dup_partition: ... (2000 dups reachable)   run_...sh: PASS
BASE arm: run_curadj_dup_partition.sh: FAIL (rc=124)   <- 124 = timeout = hang
```

and the hang is the predicted one, from `gdb -p` on the wedged base process:

```
#4  __db_pthread_mutex_condwait (mutex=94451877178064, ...)
#5  __db_hybrid_mutex_suspend (mutex=68, exclusive=1)
#6  __db_tas_mutex_lock_int (mutex=68, ...)
#8  __db_cursor_int (dbp=0x55e74a967510, ...) at src/db/db_am.c:146
#9  __dbc_newopd (...) at src/db/db_cam.c:743
#10 __bam_opd_cursor (...) at src/btree/bt_curadj.c:291
#11 __bam_ca_dup_func (...) at src/btree/bt_curadj.c:362
```

Blocked in `__db_cursor_int`'s `CQ_LOCK` (mutex 68), reached from
`__bam_ca_dup_func` via `__bam_opd_cursor`. Exactly the mechanism above.

**New regression test:** `test/db/curadj_dup_partition.c` +
`run_curadj_dup_partition.sh`, wired into `test/MANIFEST` (tier `db`). It parks
a second cursor on the record whose on-page duplicate set is about to move
off-page, then drives the conversion. It uses `DB_THREAD` deliberately — that
is the whole point — and it checks the parked cursor still addresses its
original key and can still reach all 2000 duplicates, because a mis-adjusted
cursor that does *not* hang reads the wrong row silently.

It does not use `DB_INIT_LOCK`, on purpose and with a comment saying why: with
the lock manager the parked read cursor holds a read lock on the root while the
inserts want it for write — a single-threaded self-block unrelated to what is
under test. I hit that first and diagnosed it with `gdb -p` (blocked in
`__lock_get_internal` under `__bam_get_root`) rather than working around it
blindly; it was my test's bug, not the product's.

## 5. `found`/`countp` and recovery

**Claim.** Neither the count nor the logging changes.

`found`/`countp` feeds `__bam_curadj_log`, which is replayed in recovery, so a
changed count changes recovery. Argument, per mechanism:

1. **The callbacks are untouched in their counting.** The diff changes only
   which mutex is dropped and retaken around the two re-entrant calls. No
   predicate, no `++*countp`, no `*foundp = 1` was modified. Diff confirms:
   the only lines touched in the three callbacks are `MUTEX_UNLOCK`/`MUTEX_LOCK`
   → `CQ_UNLOCK`/`CQ_LOCK` plus one added local.

2. **The set of cursors visited is identical.** The iteration order is
   unchanged (same handles, same `dblistlinks` order, same 8 partitions, same
   `TAILQ_FOREACH`). Taking the list latch shared *widens* what may run
   concurrently, but only against other **readers** — i.e. other cursor walks,
   which do not mutate the list. The exclusive/exclusive and
   exclusive/shared pairs are unchanged, so no handle can appear or disappear
   mid-walk that could not before.

3. **The rescan does not double-count.** This is the one place a count could
   move, so it is worth being precise. `*countp = 0` is in the `for`-init, so a
   `goto loop` does **not** reset it — the rescan continues accumulating. That
   is the pre-existing behavior and it is deliberate: the callbacks that trigger
   a rescan are idempotent on the second pass. `__bam_ca_dup_func` returns
   early via `if (orig_cp->opd != NULL) return (0)` ("Since we rescan the list
   see if this is already converted"), and it sets `*foundp = 1` — a flag, not a
   counter, so re-setting it is a no-op. `__bam_ca_undodup_func` requires
   `orig_cp->opd != NULL` and sets `opd = NULL` before returning
   `DB_LOCK_NOTGRANTED`, so it cannot re-fire for the same cursor; it is called
   with `countp` it `COMPQUIET`s away. `__ham_chgpg_recover_func` likewise
   ignores `countp`. So of the three rescan-triggering callbacks, none
   increments a counter, and the one that sets a flag is idempotent.

   My `ret = 0` change strictly *reduces* spurious error returns; it cannot
   change a count, because the rescan it precedes is the same rescan as before.

4. **Verified, not just argued.** `recd013` — the cursor-stability-under-
   transaction test whose whole subject is cursor adjustment being correctly
   logged and undone — passes on btree and hash, under both production and
   DIAGNOSTIC builds. `recd007`, `recd010`, `recd015` likewise (8/8 OK).

### Profiles — the fix does exactly what it was supposed to

`perf record --call-graph dwarf`, `--children` (inclusive), production builds.

**t=32:**

| symbol | base | fix |
|---|---:|---:|
| `__bam_ca_di` | 4.87% | **1.97%** |
| `__db_walk_cursors` | 4.98% | **2.01%** |
| `__log_put` | 54.17% | 56.73% |

**t=64** (where the regression is):

| symbol | base | fix |
|---|---:|---:|
| `__bam_ca_di` | 30.74% | **2.89%** |
| `__db_walk_cursors` | 31.49% | **2.97%** |
| `__log_put` | 35.36% | **56.46%** |
| `__x64_sys_futex` (kernel) | 2.60% | **0.31%** |

The fix works. At t=64 it removes **28 points** of profile from the cursor walk
and cuts kernel futex traffic 8×. The lock was exactly where the brief said.

### So why is throughput not better?

**Because the cursor walk was never the binding constraint — the log is.** At
t=64 `__log_put` goes 35.36% → 56.46%: the fix hands the freed time straight to
the next bottleneck, which absorbs all of it. Inside `__log_put`, **86.98%** of
its time is `__db_tas_mutex_lock_int` — the single log-region latch, taken by
every `__db_addrem_log` on every insert. Removing contention upstream of a
saturated serial stage cannot raise throughput; it only moves the queue.

The small *loss* at t=64 is consistent with that redistribution: threads that
previously spent time queued on `mtx_dblist` (and de-scheduled — note the 8×
futex drop) now arrive at the log latch sooner and spin there instead.
`__db_tas_mutex_lock_int` is a spin-then-suspend TAS latch, so converting
sleep-waiting into spin-waiting burns CPU that the 96 runnable threads need.
That is a hypothesis consistent with all measured numbers, not a certainty; it
does not affect the headline, which is that P4 is not this workload's limit.

### On the briefed 25.58% at t=32

I measured `__bam_ca_di` at **4.87%** inclusive at t=32, not 25.58%, on base.
I did not reconcile the difference and I am not claiming the brief's number is
wrong — a different value size, duration, or build would move it, and the
benchmark's own knobs matter. What I can say is that on the arms I measured,
at the t where the regression appears (t=64), `__bam_ca_di` **is** the largest
single term at 30.74% and the fix removes it. So the brief's qualitative
diagnosis reproduces; I could not reproduce that specific figure at that
specific t.

### Honest bottom line

P4 is a real global lock, correctly identified. Removing it is measurable in
the profile and invisible in throughput, because `__log_put` is the actual
ceiling on this workload. **On throughput this is a NULL result, with one
reproducible ~9.5% regression at t=64.** The change earns its place on
correctness grounds (section 4) and as a precondition for log work — not on
measured throughput. If the t=64 loss is judged unacceptable on its own, the
shared-latch hunk can be reverted independently of the retry-protocol fix; they
are separable, which is why the commit message separates them.
