# Cross-release benchmark: Berkeley DB 5.3.28 vs libdb LTS 2026.10.7.1 vs master (2026-10)

**Question:** has the fork improved on Oracle's last Sleepycat-licensed release, by how much, and on which
dimensions? Every access method was measured, transactional, at 1–128 threads, using the benchmarks
traditionally used to characterise an embedded transactional store.

**Answer:**
- **Concurrent reads, scans and updates are much faster on btree, hash, queue and heap.**
  - Reads (YCSB C/B) gain **1.3–2.8×** at 4–16 threads. Recno reads are mixed: 0.94–1.64×.
  - Btree and queue short range scans gain **2.6–5.3×** at 4–32 threads. Recno scans gain 1.18×.
  - TPC-C-like throughput is **4.5–7.0×** higher at 16–32 threads.
  - Run-to-run variance at 32–128 threads fell from a 13.1% median CV to 4.6%.
- **Writes that insert keys or allocate pages are slower.**
  - Transactional inserts: **0.35–0.88×** on recno, hash, btree and heap. Queue inserts are unchanged.
  - Recno updates: **0.47–0.79×**.
  - TPC-B-like with write-no-sync commit: **0.80–0.91×** at 16–128 threads.
  - Small-cache bulk loads into a queue: **0.05–0.18×**.
- **Single-threaded operations:** 0.85–1.06× (geometric mean 0.96) in the key/value workloads. The classic
  single-threaded `test_micro` suite is **0.82×** overall, with puts and mixed workloads near 0.7×.
- **The LTS and master are the same** (geometric mean of master/LTS over 168 key/value cells: 0.997). Every
  gain and every regression below was already in the LTS.
- The causes of the regressions are identified and measured (see "Why writes regressed"). Two of them are
  scalability changes whose costs land on these paths.
- **Update, v2026.10.8:** those two (R1, R2) are fixed.
  - Btree, hash and queue inserts are now 0.96–1.06× of 5.3.28 at 1–4 threads.
  - Recno updates are 0.94–1.03× at 4 threads.
  - Recno inserts at 4 threads are 0.78×.
  - Gaps remain at 16–32 threads.

  See "Addendum: v2026.10.8".

## Setup

| | |
|---|---|
| Host | EC2 **c6id.metal**: 2 × Xeon Platinum 8375C, 128 vCPU, 2 NUMA nodes, 251 GB RAM |
| OS | **Fedora 45**, kernel 7.2.11, GCC 16.2.1 |
| Storage | **XFS** on a local NVMe instance-store device (`/dev/nvme0n1`, `noatime`) |
| Tuning | performance governor, THP `never`, swap off, `numa_balancing=0`, dnf timers masked |
| bdb | Oracle Berkeley DB **5.3.28** (September 9, 2013), tag `v5.3.28`: the last Sleepycat-licensed release. 6.x and later are AGPL and excluded from this fork. |
| LTS | libdb **v2026.10.7.1** |
| master | `411e58f13` (PRs #225 and #226 not included) |

**Builds:** every arm uses the same configure (`--enable-shared --enable-static`) and
`CFLAGS="-O2 -g -std=gnu99 -Wno-error=implicit-int -Wno-error=implicit-function-declaration
-Wno-error=int-conversion -Wno-error=incompatible-pointer-types"`. The `-Wno-error` flags are needed only
because 5.3.28's configure probes use implicit-`int` `main()`, an error since GCC 14. All three select the
same mutex implementation (`HAVE_MUTEX_HYBRID` + pthreads + x86_64 assembly). The benchmark drivers link each
arm's static `libdb.a`; their md5s are in `binaries.md5`.

**Method:**
- For every (cell, rep) the three arms run back to back, and their order rotates each rep, so slow drift on
  the host cannot favour one arm.
- Each arm loads its own fresh database for every rep.
- 5 reps × 10 s per point; 3 reps for `test_micro`.
- Reported numbers are medians. A ratio marked † has a CV above 10% on one arm and should be read as a
  direction only.

## Benchmarks

1. **YCSB-style key/value** (`test/bench/xrel_kv.c`, new). Written against the 5.3 public API only, so the
   same source builds against all three. It covers **all five access methods** (btree, hash, recno, queue,
   heap).
   - Workloads: YCSB C (read-only), B (95% read), A (50% update), F (read-modify-write), E (short range
     scans, ordered methods only) and I (insert).
   - Keys: 1M records, 100-byte values, YCSB scrambled-zipfian keys (θ=0.99).
   - Transactions: every operation is a transaction (`DB_INIT_TXN`, `DB_TXN_WRITE_NOSYNC`, deadlock
     detection on conflict).
   - Metric: **committed** ops/s. Deadlocked transactions are counted separately and not scored.
   - Heap is addressed through a btree secondary from id to RID, as an application would.
2. **TPC-B-like debit/credit** (`test/bench/tproc_b.c`): scale 128 (12.8M accounts), synchronous and
   write-no-sync commit. Branch/teller/account reads use `DB_RMW`, as a TPC-B implementation does. Without
   it every arm deadlock-storms on read→write upgrades of the 128 branch rows.
3. **TPC-C-like** (`test/bench/tproc_c.c`): five transaction types, 64 warehouses, write-no-sync.
4. **Berkeley DB `test_micro`** (`test/micro`, shipped with 5.3.28): all 122 tests of `run.std`, one
   process, single-threaded. Each arm runs its own copy of the suite; the sources differ only in
   `b_uname.c`.

Thread counts: 1, 4, 16, 32, 64, 128. Raw data: `test/bench/results/xrel-2026-10/`.

## Why writes regressed (measured after the run, same host)

**R1. The deadlock detector costs more per run (the largest cause).**
- **The change:** `xrel_kv` and the YCSB defaults run detection on every lock conflict (`DB_LOCK_DEFAULT`).
  P12 (`2d8397dfe`, 2026-10-10) striped the locker table into 64 stripes, so `__dd_build` now takes all 64
  stripe mutexes (`LOCK_LOCKERS`), where 5.3.28 took one.
- **Profile:** btree insert at 4 threads, `__lock_detect` share of time: 4.3% (5.3.28) → 10.4% (master).
- **A/B:** the same binaries, each run with detection on conflict and with a 10 ms timer thread instead,
  5 reps, CV ≤ 4.8% (`dd.tsv`):

| cell | on conflict: master / 5.3.28 | 10 ms timer: master / 5.3.28 |
|---|---:|---:|
| btree insert t=4 | 0.65 | 0.92 |
| btree insert t=16 | 0.80 | 0.96 |
| heap insert t=16 | 0.78 | 0.97 |
| hash insert t=16 | 0.50 | 1.00 (both arms fall to ~9.7k/s) |

- **What it means:** an application that uses a periodic detector (the common production setup) sees most
  of the insert gap close. Hash inserts depend on immediate detection, because each hash meta-page upgrade
  deadlock otherwise waits out the timer.

**R2. The cursor-adjustment walk takes 8 mutexes.**
- **The change:** `7da0fadd3` (2026-06-19) sharded each handle's cursor queues into `DB_CURSOR_NPART` = 8.
  `__db_walk_cursors`, called on every btree/recno/hash insert and delete through `__bam_ca_di` and friends,
  now locks 8 partitions plus `mtx_dblist`, where 5.3.28 locked one mutex.
- **Profile:** single-thread btree insert, inclusive share of time: 4.7% → 14.8%.
- **A/B:** rebuilding master with `DB_CURSOR_NPART` = 1 (`np1.tsv`):
  - recovers 1.15× on single-thread inserts (0.85 → 0.98 of 5.3.28);
  - recovers 1.07–1.10× on concurrent inserts and recno updates;
  - but costs 0.83× on 16-thread btree reads, the workload the sharding was for.

**R3. The CLOCK eviction sweep examines 40–260× more hash buckets per allocation.**
- **The change:** the COOL-first CLOCK replacement (`fe471553c`, `dea815bb4`) skips HOT-band buffers in its
  normal sweep. In a cache full of freshly created dirty pages, nearly every buffer is HOT, so each allocation
  sweeps up to `MPOOL_ALLOC_SEARCH_LIMIT` (500) buckets before going aggressive.
- **Probe:** `xrel_evict_probe.c`, 1M sequential inserts, `evict.tsv`:

| cache | btree: master / 5.3.28 | queue: master / 5.3.28 | buckets examined per allocation (5.3.28 → master) |
|---|---:|---:|---|
| 1 MB | 0.80 | 0.18 | 2 → 130 |
| 4 MB | 0.73 | **0.05** | 2 → 460–520 |
| 16 MB | 0.73 | 0.79 | 0.3–1 → 80–275 |
| 64 MB (fits) | 0.85 | 0.85 | 0 → 0 |

- **Queue is hit hardest:** it also evicts 40–80× more pages (5,607 → 233,471 dirty evictions in 1 MB). The
  remaining 0.85× when the data fits in cache is the single-threaded put cost (R2 plus the write path).

**Recno** updates and inserts (0.35–0.79×) show the same detector cost (R1) plus heavy deadlocking. 41–88% of
recno update attempts deadlock in every arm, because recno renumbering locks the root. So the detector runs
far more often there.

## Addendum: v2026.10.8 (2026-10-30)

R1 and R2 above were fixed in #228 and shipped in v2026.10.8. R3 (eviction) is not fixed yet. The suite was
re-run on a fresh host of the same type: Berkeley DB 5.3.28, v2026.10.7 (the previous regular release, which
equals the LTS here), and the v2026.10.8 candidate: master `4cfe5f175` after #228. The tag adds only the version strings.
Raw data is in `results/xrel-2026-10/v2026.10.8/`.

**Setup differences from the main run:** 3 reps instead of 5, threads 1/4/16/32 (no 64/128), and `test_micro`
was not re-run (its code paths did not change). Five btree cells (A at t=1–32 and F at t=1) were re-run in full,
because a test job shared the host for three minutes during their first pass. **Heap inserts were not
re-measured.** The heap I rows were lost when the host was torn down before their copy completed. The
release A/B below covers heap inserts at 16 threads (1.07× vs master on Linux x86_64).

**What changed, v2026.10.8 ÷ v2026.10.7, key/value (108 cells):**
- Inserts: btree 1.13× (t=1) and 1.43× (t=4); hash 1.08–1.49×; recno 1.19–1.64× at t≥4.
- Recno updates and 95% reads: 1.22–1.88× at t≥4. Recno renumbering locks the root, so these deadlock often
  and paid the detector cost on every conflict.
- Everything else (84 cells): 82 are within 0.93–1.10. The other two are recno E t=32 (0.86) and heap B
  t=16 (0.91 †), a scan and a read, which neither change touches. The geometric mean over all 108 cells is 1.06.

**What is still slower than 5.3.28:**
- Inserts at 16–32 threads: btree 0.78–0.90×, hash 0.83–0.90×, recno 0.54–0.78× (t≥4). In btree every
  thread appends to the same last page in every release. Profiling shows the time is the page-lock wait in
  `__bam_search`.
- Recno read-modify-write at 16–32 threads: 0.77–0.81×.
- TPC-B-like with write-no-sync at 16–32 threads: 0.79–0.81× (the same as v2026.10.7; neither change moves it).
- Single-threaded: geometric mean 0.98 across 27 cells (0.94–1.06).

## Not covered and caveats

- **No real TPC results.** TPC-B-like and TPC-C-like are not the TPC benchmarks and are not comparable with
  TPC results.
- **Single-socket placement was not separated from cross-socket.** Threads were not pinned, so the 64- and
  128-thread cells span both NUMA nodes; that is where most † marks are.
- **Durability:** write-no-sync was measured throughout; sync commit was measured for TPC-B only.
- **MVCC, SSI and replication** were not exercised.
- **Harness bug, fixed:** a harness bug was found and fixed during the follow-up experiments. After the
  measured window, workers stopped retrying while on-conflict detection was never re-triggered, so a residual
  deadlock cycle could hang a process at shutdown. The fix keeps a detector running until all workers have
  joined. The main run is unaffected: all 2,520 key/value rows completed their full 10 s window.
