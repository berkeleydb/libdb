## Upgrading to libdb 2026.10.7.1

libdb 2026.10.7.1 is the first patch release of the 2026.10.7 long-term support (LTS) line. It contains bug fixes only.

**No upgrade procedure is needed.** The shared-memory region format, the database and log formats, the soname and the public ABI are the same as 2026.10.7 on every platform. An environment created by 2026.10.7 opens with 2026.10.7.1 and the other way round, and processes from both releases can share one environment. Install it in place of 2026.10.7.

### Build signatures

The signature depends on the platform and the configure options. On each
platform below, 2026.10.7 and 2026.10.7.1 built the same way print the same
value.

| Platform (default `configure`) | 2026.10.7 | 2026.10.7.1 |
| --- | --- | --- |
| Linux x86_64 (Debian 12, gcc) | `0x841f4ea8` | `0x841f4ea8` |
| FreeBSD aarch64 (14.5, clang) | `0x56a06689` | `0x56a06689` |
| FreeBSD x86_64, macOS arm64, Windows | unchanged | unchanged |

### What it fixes

**A reverse cursor walk could skip records (`DB_PREV`).** Btree and Recno cursors read their position through two C types that the compiler treats as unrelated. Under strict-aliasing optimisation a compiler may reorder those reads and writes. FreeBSD's clang at `-O2` on 64-bit ARM does: `DB_PREV` tested the slot it had just left, so a reverse walk silently skipped live records next to deleted ones. A debug build (`--enable-diagnostic`) crashed instead. The positions are now read through the type that writes them. Forward walks (`DB_NEXT`) were not affected. If you build with clang on aarch64 and walk cursors backwards over data with deletes, upgrade. Every release back to Berkeley DB 5.3.28 has this code, and the defect is undefined behaviour on every compiler, so builds elsewhere are fixed too.

**`DB_TRUNCATE` with a subdatabase name destroyed the whole file.** `DB->open` with `DB_TRUNCATE` and a subdatabase name was accepted. It truncated the entire file to zero bytes, destroying every other subdatabase in it, and then failed with `EBADF`. The documentation already said `DB_TRUNCATE` cannot be used on a database within a file. It is now refused with `EINVAL` (`BDB5384`), and the file is not touched. `DB_TRUNCATE` on a whole file (no subdatabase name) works as before. An application that relied on the old behaviour was losing data. If you need to empty one subdatabase, use `DB->truncate`.

**A lock-order inversion when discarding a written file from the cache.** When the last handle on a file with unflushed writes closed, libdb flushed the file while holding the cache's allocator latch, and the flush takes the file's hash-bucket latch. That is the reverse of the order every other path uses. A debug build (`--enable-diagnostic`) has a lock-order checker, and it stopped the process with `BDB2077 LOCK ORDER VIOLATION` and `DB_RUNRECOVERY`. A `DB_TRUNCATE` open of an existing file was one way to reach it. A release build has no checker and carried on, but the inverted order is a latent deadlock against threads that take the two latches the other way round. The flush now happens before the allocator latch is taken.

Each fix has a regression test that fails on 2026.10.7 and passes on 2026.10.7.1: `test/db/run_bamc_prev_alias.sh`, `test/db/run_truncate_subdb.sh` and `test/db/run_mf_discard_order.sh` (the last one in a `--enable-diagnostic` build).

### Also in this release

- The five Windows Visual Studio solution and project files are stored with normalised line endings, so a fresh checkout no longer shows them as modified.
- CI runs the `test/db` tier against the plain pthreads mutex on Linux as well as the default hybrid mutex.
- The upgrade guide lists the 2026.10.6 and 2026.10.7 upgrade notes.
