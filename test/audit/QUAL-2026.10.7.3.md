# v2026.10.7.3 qualification (LTS patch release, 2026-11-04)

The third patch release of the `2026.10.7` LTS line, qualified against the
gates for an LTS patch release in [`QUALIFICATION-MATRIX.md`](QUALIFICATION-MATRIX.md)
(gates 1–5 and 7, plus L1–L4). The candidate was compared with the base tag
`v2026.10.7.2` (`2625d8cd7`), both built the same way on the same host.

**Candidate:** `release/2026.10.7.3`. The release commit `f09a8f246` (PR #271)
on `lts/2026.10.7` at `f2e1b768c`. The FreeBSD hosts qualified `d12fe79e1`
(the four backports merged locally, then the release commit). Linux qualified
`43f4a560b`, one commit earlier. The release differs from what was qualified in
two test-only commits, and in no library source:

- `8bec6e80b` (from #268): `lock_order_check`'s new arm returns `int`, so clang
  builds it. gcc had already built and run the old version on Linux.
- `a0772e835` (#273, from #272): `test/c/leak-run.sh` puts `src/` on its include
  path. #269 made `lock_order_check.c` include `db_int.h`, so the CI leak job
  could not build it. The qualification scripts build `lock_order_check`
  through the Makefile, which already had `src/`.

**Hosts:** EC2, on-demand, AWS account `woof`:

| Host | OS | vCPU | Compiler |
|---|---|---|---|
| Linux x86_64 | Debian 12, c6i.8xlarge | 32 | gcc |
| FreeBSD x86_64 | FreeBSD 14.5, c6i.4xlarge | 16 | clang |
| FreeBSD aarch64 | FreeBSD 14.5, c7g.4xlarge | 16 | clang |

**How gate 1 was counted.** The tier has 38 runners in `test/MANIFEST`. Each
row counts runner verdicts (`run_*.sh: PASS`) plus four runners that print a
`VERDICT … PASS` line instead (`qam_inorder_consume`, `r1_revive`,
`r2_dup_revive`, `r2_fuzz`), so every runner is accounted for. The summary line
in the raw output reports `fail=2` or `fail=3`. Two of those are lines from
`run_rep_cmpvote_order`'s sabotage arm, which must print `FAIL` and did. On
FreeBSD the third is `run_qam_extent_vrfy` (†).

The skips are environmental: no JDK (`u8_backup_config`, `u9_serializable`), no
meson on FreeBSD (`meson_autoconf_parity`), and `mvcc_mtx_doublefree` when
failchk reclaims no mutex, so its scenario is never built.

**† `run_qam_extent_vrfy` on FreeBSD** timed out at its 600 s limit in all three
tier runs on both hosts, as it did for v2026.10.7.2. Run alone with
`TIMEOUT=1200` on the same hosts, the base and the release take the same time
and both pass: x86_64 640 s / 640 s, aarch64 600 s / 601 s. The hosts use their
EBS root (UFS with soft updates). The limit on the line stays at 600 s, since
GitHub's runners need about 181 s.

**L2 `.text`.** On Linux, `nm -S` shows that only the four fixed functions
changed size: `__bam_defdecompress` +161 bytes, `__bamc_start_decompress` +64,
`__memp_dirty` +30 and `__rep_cmp_vote` −22, net +233 of the +240. The other
seven bytes are alignment. On FreeBSD, clang's `.text` shrank by 1,232 and
1,824 bytes. The per-function sizes there were not captured before the hosts
were torn down. The region signature, the handle sizes and the exported symbols
are unchanged on every host.

**L3, the election comparator.** `rep_cmpvote_order` carries a verbatim copy of
`__rep_cmp_vote`, and its drift check confirms the copy matches the candidate's
`src/rep/rep_elect.c`. Its pre-fix arm is the v2026.10.7.2 function. That arm
must fail, picking different winners in different arrival orders, and did on
every host. The fixed copy passes.

**L3, the lock-order checker.** `lock_order_check` from the candidate tree was
built against each diagnostic library. The base reports `BDB2077` and aborts in
the two-env arm (status `0x6` on Linux, `0x86` on FreeBSD, SIGABRT with and
without a core). The release passes. The control and `lk_partitions=1` arms pass
on both.

**Gate 6** (the metal benchmark) was not run. None of the fixes is on a hot
path: the decoder change adds bounds checks to compressed B-tree reads only,
the comparator runs once per vote during an election, the `BDB3010` change is
on an abort path, and the lock-order change is diagnostic-only. **Gate 8** (the
soak) was not run, because no fix changes resource lifetime.
