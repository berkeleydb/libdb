## Upgrading to libdb 2026.10.7.3

libdb 2026.10.7.3 is the third patch release of the 2026.10.7 long-term support (LTS) line. It contains bug fixes only.

**No upgrade procedure is needed.** The shared-memory region format, the database and log formats, the soname and the public ABI are the same as 2026.10.7, 2026.10.7.1 and 2026.10.7.2 on every platform. An environment created by any of them opens with 2026.10.7.3 and the other way round, and processes from all four releases can share one environment. Install it in place of 2026.10.7.2.

In a replication group that mixes 2026.10.7.3 with earlier releases, see the election fix below.

### Build signatures

The signature depends on the platform and the configure options. On each
platform below, 2026.10.7 through 2026.10.7.3 built the same way print the
same value.

| Platform (default `configure`) | 2026.10.7.2 | 2026.10.7.3 |
| --- | --- | --- |
| Linux x86_64 (Debian 12, gcc) | `0x841f4ea8` | `0x841f4ea8` |
| FreeBSD aarch64 (14.5, clang) | `0x56a06689` | `0x56a06689` |
| FreeBSD x86_64, macOS arm64, Windows | unchanged | unchanged |

### What it fixes

**A replication election could choose a site with older data.** Each site ranks the votes it receives to pick a winner. The ranking was meant to prefer the site with the newest data, but its last rule, used when two sites' logs end at the same position, ignored which generation of data each site held. Two candidates with logs ending at the same position but different data generations were ranked by whichever vote arrived last. If a majority of sites counted the older site's vote last, that site won, and the site with newer data rolled back its log to match on its next sync, losing transactions it had already acknowledged as durable. The first vote counted was also handled separately, so ties could resolve differently from site to site. The ranking is now one fixed order, applied to every vote the same way: sites that can be elected, then non-zero priority, then newest data generation, then log position, priority, the random tiebreaker and the site's ID. It no longer depends on arrival order, and it never ranks older data above newer.

This needs two candidates whose logs end at exactly the same position, so it is rare. The conditions were reproduced on real sites; that a network delivers the votes in the losing order is argued, not shown end to end. `test/db/run_rep_cmpvote_order.sh` runs the vote values captured from those sites through every arrival order. It fails on 2026.10.7.2 and passes on 2026.10.7.3.

During a rolling upgrade, old and new sites rank the affected ties differently, so in that case an election may need an extra round before the sites agree. It cannot produce two masters. Finish the upgrade promptly.

**A corrupt compressed B-tree record could crash the reader.** A B-tree opened with `DB->set_bt_compress` stores records in a compressed form that includes length fields. The decoder trusted those lengths, and a page comes from disk:

- it read each length field before checking that the bytes were there, so a truncated record read past its end;
- it added two lengths without checking for overflow, so a large enough value wrapped around, passed every size check, and made it copy about 4 GB;
- the first record in each group had its length used with no check at all, so one corrupted byte in the file crashed a plain `DB->get`.

Each length is now checked before it is read or used, and a bad record returns `EINVAL`. Only B-trees with compression enabled, in builds configured with `--enable-compression`, are affected. `test/db/run_bt_decompress_bounds.sh` has five cases, including a real database with one length byte corrupted on disk. All five crash on 2026.10.7.2 and pass on 2026.10.7.3.

### Also in this release

- An SSI transaction that aborted with `DB_SNAPSHOT_CONFLICT` or `DB_SNAPSHOT_UNSAFE` while upgrading a page for writing also printed `BDB3010 error getting a page for writing`. The abort was correct and nothing was lost. The message is gone; the return codes are unchanged.
- In a build configured with `--enable-diagnostic`, the lock-order checker reported a deadlock, and panicked the environment, when a thread held a latch in one environment and took the same-numbered latch in another. A replication application whose send callback writes to a second environment hit it, as did every replication election test. Latches in different environments are no longer compared. Release builds do not include the checker.
