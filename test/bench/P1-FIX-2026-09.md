# P1: the locker table took all 64 stripes per transaction

Branch `fix/p1-locker-stripes`. Measured on the 96 vCPU EC2 box (`m7i`-class,
185 GiB, `/nvme` XFS), base = `b5a811115`.

## The defect

`LOCK_LOCKERS` was a serial loop over every entry of
`region->mtx_locker_stripe[]` (`LOCK_LOCKER_STRIPES` = 64). Every locker create
and every locker free took it, so each transaction acquired and released **128
sleeping mutexes** on the locker table. The striping the structure was given was
defeated by its own writers: 64 latches behaved as one, plus 64x the acquire
cost.

`__lock_getlocker` (`lock_id.c:274`) is the site `txn_begin` reaches
(`txn.c:588`) and `__lock_freelocker` (`lock_id.c:615`) is the site `txn_end`
reaches (`txn.c:1916`) — **not** `__lock_id`, which only serves the explicit
`DB_ENV->lock_id` API. `__lock_id` is converted too, but it is not the hot one.

## Two premises in the original diagnosis that did not survive contact

Both changed the design, so they are recorded here rather than quietly fixed.

**1. An id-keyed stripe does not own the chain its holder walks.** The
pre-existing `RDLOCK_LOCKER(env, region, id)` keyed the stripe on
`LOCK_LOCKER_STRIPE(id) = id & 63`, while the bucket is
`LOCKER_HASH` = `id % region->locker_t_size`, and `locker_t_size` is a **prime**
from `__db_tablesize` (1031, 4099, …). So `id` and `id + locker_t_size` share a
bucket but land in different id-keyed stripes: with the default table, ids 1 and
1032 are one chain, two stripes. Taking `mtx_locker_stripe[id & 63]` therefore
does **not** exclude a second writer from the same chain. That is exactly why the
original code had writers take all 64. The fix keys the stripe on the **bucket
index** instead — `LOCK_LOCKER_ID_STRIPE(region, id)` =
`LOCK_LOCKER_STRIPE(id % locker_t_size)` — which makes a stripe the sole owner of
every chain that maps onto it. `RDLOCK_LOCKER`/`RDUNLOCK_LOCKER` changed key with
it, so the existing reader at `lock.c:864` stays coherent with the writers.

**2. There is no "common path that touches only one stripe."** Beyond the bucket
chain, `__lock_getlocker_int` pops `region->free_lockers`, pushes
`region->lockers` (the `ulinks` list every full-table walk uses), and bumps
`region->nlockers`/`stat.st_lockers`; `__lock_freelocker_int` does the inverse.
None of that is per-bucket, and on this workload create/free **is** the common
path (every `txn_begin` allocates a fresh id). So one bucket latch alone cannot
be correct.

The fix is therefore **two latches, not one**: `mtx_locker_stripe[0]` is
repurposed as the locker **allocation latch** (guarding
`free_lockers`/`lockers`/`nlockers`/`lock_id`/`cur_maxid`), and the bucket stripe
nests inside it. 128 mutex operations per transaction become 4 — 2 when the
bucket happens to map onto stripe 0 and the nested acquire is skipped.

Reusing stripe 0 rather than adding a `db_mutex_t` to `__db_lockregion` is
deliberate: `src/env/env_sig.c` hashes that struct, so a new field would change
the environment signature and break attach-in-place for every existing
environment. Cost of the reuse: readers whose bucket maps onto stripe 0 (1 in 64)
block behind any writer anywhere. Documented at the macro.

| `lock_id.c:615` | `__lock_freelocker` | **converted** | The `txn_end` path. Alloc latch + 1 bucket. Escalates when the locker has family links. |
| `lock_id.c:72` | `__lock_id` | **converted** | Alloc latch across the counter test+bump; 1 bucket for the insert. Escalates for the id-wraparound rebuild, which walks `region->lockers`. |

| `lock_id.c:213` | `__lock_id_free` | **left** | Same, and it is reached from `db.c:1138` for in-memory-database fileid lockers, not from a hot path. |

| `lock_id.c:657` | `__lock_familyremove` | **left** | Unlinks from the master locker in another bucket. Same reason. |
| `lock_id.c:579` | `__lock_sireap_lockers` | **left** | Walks all of `region->lockers`. |

## Race-freedom of `region->lock_id` / `cur_maxid`

Choice: **a dedicated mutex — `mtx_locker_stripe[0]`, reused as the allocation
latch.** Not an atomic.

An atomic increment would be wrong here, not merely awkward. The wraparound
logic is a read-modify-write **spanning three statements**: the
`lock_id == DB_LOCK_MAXID` normalisation, the `lock_id == cur_maxid` test, and
the `++`. Two counters must move together, and the rebuild between them walks a
shared list and calls `__os_malloc`. An atomic on `lock_id` alone would let a
second thread observe `lock_id == cur_maxid` and enter the rebuild concurrently
with a thread already inside it, producing two different id spaces.

The argument:

- Every read and every write of `lock_id` and `cur_maxid` in `__lock_id` happens
  with stripe 0 held, and stripe 0 is held **continuously** from before the
  normalisation to after the `++`. No concurrent bump can interleave between the
  test and the increment, and the rebuild is single-threaded with respect to any
  other allocator.
- The rebuild additionally takes stripes 1..63 (`LOCK_LOCKERS_REST`) before
  touching `region->lockers`, so the list walk excludes every bucket reader and
  writer. The resulting hold is exactly `LOCK_LOCKERS`, acquired in the same
  ascending order.
- The only other writer is `__lock_id_set`, which is documented test-only and
  single-threaded (it took no latch before this change either).
- `lock_stat.c:100` reads both under `LOCK_REGION_LOCK` for reporting, where a
  stale value is a display artifact, not a correctness issue. Unchanged.
- `free_lockers` has the same property and it is what licenses the
  single-bucket choice: **every** consumer of the free list holds stripe 0, so a
  list observed non-empty under stripe 0 cannot go empty underneath the caller,
  and the all-stripes refill branch inside `__lock_getlocker_int` is then provably
  unreachable. That test-then-call, both under stripe 0, is the whole
  correctness hinge of the conversion.

## Lock ordering

- **Stripe 0 first, released last.** Every converted path takes the allocation
  latch before any bucket stripe and drops it after.
- **Never two bucket stripes.** No converted path holds more than one. That is
  why `addfamilylocker`/`familyremove` were left alone — they inherently reach two.
- **`LOCK_LOCKERS` is a superset in the same order** (ascending from 0), and
  `LOCK_LOCKERS_REST` takes 1..63 while 0 is already held, so escalation
  produces the identical hold set with the identical acquisition order. An
  escalating thread and a `LOCK_LOCKERS` thread cannot deadlock.
- **Non-recursive latches respected.** `LOCK_LOCKER_BUCKET` skips the acquire
  when the bucket's stripe *is* stripe 0.
- **Cross-subsystem order unchanged.** No new nesting was introduced: the
  converted paths take locker latches only, and the pre-existing
  `LOCK_LOCKERS -> LOCK_REGION_LOCK` (refill) and `LOCK_LOCKERS -> partition`
  orders are untouched.
- All 64 stripes share `MTX_LOCK_REGION`, one rank (`DB_LO_RANK_LOCK_PART`), and
  siblings are deliberately unordered there — so the checker does not report
  sibling nesting, and the argument above is what carries the soundness. The
  checker still covers the cross-rank claim (no locker stripe is taken under a
  lower-ranked latch).

**Checker result: did not fire.** 20 s, 32 threads, through the converted
create/free paths, linked against the `--enable-diagnostic` library
(`DIAGNOSTIC` defined in `db_config.h`, `__db_lo_acquire`/`__db_lo_check` present
in the `.so`): **0 bytes on stderr**. Full `ssi001`–`ssi011` also ran on that
build with no violation line.

## Shape — the headline claim

Median ops/s normalised to each arm's own t=1:

| arm | t=1 | t=8 | t=32 | t=96 |
|---|---|---|---|---|
| base | 1.000x | 0.992x | 0.883x | 0.706x |
| fix | 1.000x | 0.940x | 0.932x | 0.828x |

**Honest answer: the shape is improved but not fixed.** On this harness the
base arm did *not* reproduce the briefed "peak at t=8" — it peaked at t=1 and
decayed monotonically (0.992 → 0.883 → 0.706), so the premise the shape claim
was to be tested against is not what this box shows today. What the fix does
change:

- The t=32 **dip is gone**: base falls 0.992 → 0.883 from t=8 to t=32 (a real
  drop); fix is flat, 0.940 → 0.932.
- The t=96 retention improves from 0.706x to 0.828x, and the absolute t=96
  number (102,377) now **exceeds base's best point at any thread count**
  (95,324 at t=1).
- Run-to-run stability at t=96 improves nearly tenfold: CV 11.13% → 1.29%. A
  convoy is what produces that variance, and it is gone.

So: throughput no longer degrades from t=8 to t=32, and it climbs in absolute
terms past every base point — but it still does not increase monotonically with
thread count. The remaining decay is elsewhere (see the profile: 64% of time is
still in `__db_tas_mutex_lock_int`, now on other latches).

## Profile, t=96, `--call-graph dwarf`

Inclusive (children) share, same harness, 20 s, 96 threads:

| symbol | base | fix |
|---|---|---|
| `__lock_getlocker` (incl.) | **9.10%** | 1.61% |
| `__lock_freelocker` (incl.) | **9.55%** | 1.31% |
| **locker path, summed** | **18.90%** | **4.29%** |
| `native_queued_spin_lock_slowpath` (self, kernel) | **3.22%** | **0.01%** |
| `__db_tas_mutex_lock_int` (self) | 82.33% | 64.20% |

The kernel spinlock slowpath — the sleeping-mutex futex contention the
diagnosis identified — is **eliminated** (3.22% → 0.01%). The locker path drops
**4.4x**. `__db_tas_mutex_lock_int` remains dominant but now over the remaining
latches, and real work becomes visible in the profile for the first time
(`__bam_ca_di_func` 6.14%, `__memp_alloc`, `__memp_fget`, `__bam_cmp`), which is
what a removed convoy looks like.

`lock_wait` rises with the fix (68,892 → 130,024 at t=96). That is expected and
is not a regression: it counts *lock-manager* waits over a 1.5x larger
transaction volume in the same wall clock. Per operation it is roughly flat.

### One asymmetry chased to ground

The fix arm's `db_verify` emitted many `BDB2034 unable to allocate memory for
mutex; resize mutex region` warnings where base, at first, emitted none. That is
a **database-size artifact, not a defect** — proven by running base long enough
to exceed the fix's row count:

| arm | secs | rows | db file | BDB2034 count | `db_verify` rc |
|---|---|---|---|---|---|
| base | 40 | 1,851,066 | 623 MiB | 121,456 | **0** |
| fix | 28 | 1,814,073 | 574 MiB | 115,106 | **0** |

At comparable size **base produces more warnings than fix**. The warning tracks
row count in both arms, `db_verify` returns 0 and prints `succeeded` in every
case. A locker-leak probe (the shape that would exhaust the mutex region) was
also negative: after 1.4M/1.7M transactions both arms report `2` lockers
allocated and `0` current.
